# Эксплуатация

Процедуры для тестовой среды и рабочего сервера. Установка с нуля и настройка инвентаря подробно описаны в [README](../README.md); здесь — как этим пользоваться и что делать, когда что-то идёт не так. Причины решений — в [DECISIONS.md](DECISIONS.md).

## 1. Главное правило запуска

- Все команды — из папки `ansible/`.
- **Тестовая среда:** `ansible-playbook site.yml` (инвентарь по умолчанию).
- **Рабочий сервер:** только `ansible-playbook -i inventory/prod site.yml`, сначала с `--check --diff`.
- Окружения запускаются **по отдельности**: пароль sudo спрашивается один раз на запуск.
- Файлы MaxApoc (compose, `gateways.json`, наблюдаемость) Ansible берёт **из чистого клона `main`** (`~/.cache/infra-lab/APP_REPO`), который сам обновляет первой задачей; рабочая копия не участвует ([ADR-019](DECISIONS.md#adr-019)). Ручные правки в клоне останавливают запуск: `git -C ~/.cache/infra-lab/APP_REPO checkout -- .`.
- Рабочий сервер должен получить **ровно то, что проверено в тестовой среде**: после запуска тестовой среды запомнить `git -C ~/.cache/infra-lab/APP_REPO rev-parse HEAD` и запускать рабочий сервер с `-e maxapoc_repo_version=<хеш>`.
- **Версию прокси Ansible не меняет:** её выкатывает деплой из CI (раздел 5).
- Каждый неожиданный `changed` разбирается **до** рабочего сервера.

## 2. Подготовка сервера с нуля

Чистая машина с Ubuntu 24.04 превращается в рабочий сервер одной командой; повторный запуск ничего не меняет.

**Что нужно заранее**
- Управляющая машина: `ansible-core` 2.18+, коллекции (`ansible-galaxy collection install -r requirements.yml`), локальная копия MaxApoc, пароль vault своего окружения.
- Целевой сервер: Ubuntu Server 24.04, от 1 ГБ RAM, `openssh-server`, **отдельный пользователь с sudo по паролю** и SSH-ключом управляющей машины. Вход под root не нужен и после запуска будет запрещён.
- Инвентарь окружения, `vault.yml` с секретами окружения, сертификат сервера от CA проекта (`ca.key` на сервер не попадает).

**Запуск**
```bash
ansible-playbook site.yml --check --diff     # предварительный просмотр (прогноз)
ansible-playbook site.yml                    # применение
ansible-playbook site.yml                    # повтор: ожидается changed=0
```

**Время** (тестовая среда, через HTTP-прокси лаборатории): полный прогон на чистой ВМ — **6 мин 05 с** (02.11.2026; раньше, со сборкой образа на сервере, — 15 мин 25 с); повторный прогон без изменений — ~1,5 минуты.

**Проверка результата** — README, раздел «Проверка».

**Почему повторный запуск безопасен.** Задачи описывают состояние, а не действия. Там, где нужны команды (swap), они защищены проверкой текущего состояния. sshd, Docker и сервисы стека перезапускаются только при изменении их конфигов; перезапуски стека мониторинга выполняются **до** проверки его здоровья (`flush_handlers`), поэтому проверяется итоговое состояние. Версию прокси (`release.env`) Ansible создаёт только на сервере, где её нет.

**Чистый сервер** ([ADR-007](DECISIONS.md#adr-007)): Ansible поднимает прокси на **начальной** версии из `maxapoc_proxy_image` в инвентаре, затем первый деплой приносит актуальную. Начальную версию держать свежей (обновлять при пересборках с нуля): очень старый образ может не совпасть с текущим compose.

```bash
ssh -q -o IdentitiesOnly=yes -i <ключ_деплоя_окружения> maxapoc-deploy@<адрес_сервера> 'deploy sha256:<digest актуальной версии>'
```

Проверено 02.11.2026: чистая ВМ → один запуск без ошибок → первый деплой (1 мин 09 с) → повторный запуск `changed=0`.

## 3. Перевод работающего сервера на этот код

Первый запуск на сервере, где уже что-то работает, — это **миграция**: для каждой задачи нужно знать, что совпадёт, что перезапишется и что перезапустится. Порядок, по которому переведён рабочий сервер 28.10.2026:

**Подготовка (заранее, днём)**
1. **Разведка только чтением:** ОС, swap, `ufw status numbered` и `verbose`, `ss -tulpn`, `sshd -T`, источники apt, `daemon.json`, `apt-mark showhold`, пакеты Docker, контейнеры, `docker stats`, сети Docker.
2. **Пользователь вместо root:** создать, ключ, проверить вход **только ключом** из второй сессии; первую не закрывать. Проверить консоль хостера (запасной вход) и пароль root в менеджере паролей.
3. **Сверка секретов** с vault по хешам (секреты не выводятся), **сверка кода** по хешам файлов. Если код отличается — перевод станет ещё и обновлением приложения.
4. **Репетиция** в тестовой среде с копией «как на рабочем сервере» (тот же каталог, пользователь, код); замер простоя и проверка отката.
5. **Предпросмотр** `-i inventory/prod --check --diff`: каждое `changed` объяснено. Конфликты между файлами (apt, sshd) предпросмотр не видит — ищутся при разведке.
6. Снимок или резервная копия VPS у хостера.

**Во время работ** (в часы минимальной нагрузки по графику запросов)
- Терминалы: рабочая сессия на сервере (не закрывать), запуск плейбука, счётчик доступности прокси, новые SSH-подключения для проверки.
- Список контейнеров **до**: `sudo docker ps --format '{{.Names}}' | sort > ~/containers-before.txt`.
- Страховки отката: метка старого образа, копия заменяемых файлов.
- Запуск с записью лога **вне репозитория**.

**Проверки после — по порядку, при провале откат этого слоя**
1. SSH: ключ работает; пароль и root отклоняются; `sshd -T` → `no` у `permitrootlogin`, `passwordauthentication`, `kbdinteractiveauthentication`.
2. ufw: политики, список правил; удаление старых правил; сразу новое SSH-подключение.
3. Docker и apt: `daemon.json`, `apt-mark showhold`, `apt-get update` без ошибок.
4. **Все контейнеры вернулись:** `sudo docker ps --format '{{.Names}}' | sort | diff ~/containers-before.txt - && echo ALL_BACK`.
5. Прокси: образ, `healthy`, uid, лог без ошибок прав, простой по счётчику, TLS с `--cacert`.
6. Всё, что зависит от сервера: VPN, панель, WireGuard, Zabbix хостера, мониторинг, запрос из приложения.
7. Повторный запуск — `changed=0`.

**Откат по слоям**

| Что сломалось | Откат (из рабочей сессии или консоли хостера) |
|---|---|
| Прокси | `sudo docker compose -f /opt/maxapoc/proxy/vps/docker-compose.yml down && sudo docker compose -f <старый каталог>/docker-compose.yml up -d` |
| Нужный порт закрылся | `sudo ufw allow <порт>/<proto>`; в крайнем случае `sudo ufw disable` из консоли |
| Нет входа по SSH | `sudo rm /etc/ssh/sshd_config.d/00-hardening.conf && sudo systemctl reload ssh` |
| Docker после `daemon.json` | `sudo rm /etc/docker/daemon.json && sudo systemctl restart docker` |
| apt | вернуть сохранённый файл источника |

После отката слоя — сначала причина, потом повторный запуск: иначе он вернёт ту же поломку.

**Уборка через 1–2 недели** (если всё это время без замечаний)
```bash
sudo docker ps --format '{{.Names}} {{.Label "com.docker.compose.project.working_dir"}}' | grep maxapoc-proxy   # /opt/...
sudo rm -rf <старый каталог прокси> <сохранённые копии файлов>
sudo docker network rm vps_default
sudo docker image rm vps-maxapoc-proxy:pre-ansible vps-maxapoc-proxy:latest
```
**Без** `docker compose down` из старого каталога: у старого и нового каталога одно имя compose-проекта, команда остановит текущий прокси.

Уборка на рабочем сервере выполнена 02.11.2026 (журнал работ).

## 4. Работы с Docker на сервере

- Любая работа, которая может перезапустить демон Docker (изменение `daemon.json`, обновление пакетов): список контейнеров до и сравнение после (раздел 3, шаг 4).
- `live-restore` (роль `docker`): перезапуск демона не останавливает контейнеры. Включено на обоих серверах; на рабочем — 30.10.2026 без перезапуска демона: `daemon.json` записан вручную ровно как шаблон роли, `sudo dockerd --validate --config-file /etc/docker/daemon.json`, `sudo systemctl reload docker` ([ADR-011](DECISIONS.md#adr-011)).
- **Образы — без `docker image prune -a`:** он удалит предыдущий образ, на который опирается откат без реестра. Деплой сам оставляет только текущий и предыдущий образ; удалять вручную — только явным списком (`docker image rm <образ>`).
- **Ручной compose прокси — только с обоими файлами переменных:** `cd /opt/maxapoc/proxy/vps && sudo docker compose --env-file .env --env-file release.env <команда>`. Без них compose остановится с подсказкой.
- Проверка: `sudo docker info --format '{{.LiveRestoreEnabled}}'`.
- Сравнивать перезапуск контейнеров по `docker inspect --format '{{.State.StartedAt}} {{.RestartCount}}'`, а не по строке `Up …` в `docker ps`: она округлена.

## 5. Деплой прокси

**Поток.** Все изменения идут `dev` (проверки) → `main`. Слияние в `main`, которое меняет `proxy/**` или `.github/workflows/proxy.yml`, **само выкатывает прокси на рабочий сервер**: `test` → `image` (образ в GHCR, digest в сводке запуска) → `deploy` (окружение `production`, проверка «коммит есть в `main`», `deploy <digest>` по SSH). Изменения только в `observability/**` образ не пересобирают. Сборка APK от изменений прокси не запускается. Поэтому в `dev` — только то, что можно выкатить ([ADR-021](DECISIONS.md#adr-021)).

**Срочное исправление прокси**, если в `dev` лежит то, что выпускать нельзя: ветка от `main` → слияние в `main` (деплой) → `main` вливается в `dev`.

**Что делает сервер** ([ADR-018](DECISIONS.md#adr-018)): скачивает образ → сохраняет прошлую версию в `release.env.prev` → пишет новую в `release.env` → пересоздаёт контейнер и ждёт healthy до 60 с → `OK` и удаление лишних образов, или автооткат. Простой — около 1 с на пересоздание; подтверждение — несколько секунд.

**Результат деплоя** (аннотация в CI и код выхода скрипта):

| Код | Значит | Что делать |
|---|---|---|
| 0 | выкачено, healthy | проверка после деплоя (ниже) |
| 1 | неверный ввод (не прошёл фильтр) | проверить, что передаётся digest из задачи `image` |
| 2 | образ не скачался, **ничего не изменилось** | доступ к GHCR и срок токена реестра на сервере |
| 3 | идёт другой деплой | дождаться и повторить |
| 4 | новая версия не стала healthy, **откат выполнен** | `docker logs`, исправить, выпустить новую версию |
| 5 | откат не удался — **прод требует внимания** | вход на сервер, раздел 6 |
| 255 | SSH не подключился | `DEPLOY_HOST`, `DEPLOY_KNOWN_HOSTS` (ключ хоста менялся?), `LIMIT` ufw |

**Проверка после деплоя** ([ADR-022](DECISIONS.md#adr-022)) — 15 минут после выкладки смотреть оповещения в Telegram и панель прокси. На рабочем сервере оповещения прокси (`MaxapocServerErrors`, `MaxapocProxyDown` и др.) вычисляет стек `hobot-metrics`: его копия правил обновляется вручную при каждом изменении `observability/prometheus/` в MaxApoc.

**Что сейчас работает** — ручной запуск workflow `Proxy` с ветки `main` (Actions → Run workflow): задача `deploy-check` выводит образ и состояние с сервера; ручной запуск ничего не выкатывает. На сервере:
```bash
sudo docker inspect maxapoc-proxy --format '{{.Config.Image}} {{.State.Health.Status}}'
sudo cat /opt/maxapoc/proxy/vps/release.env /opt/maxapoc/proxy/vps/release.env.prev
sudo journalctl -t maxapoc-deploy-gate -t maxapoc-deploy-run --since today --no-pager
```

**Тестовая среда** из CI недоступна (NAT); там деплой выполняется вручную с управляющей машины той же командой, что делает CI:
```bash
ssh -q -o IdentitiesOnly=yes -i ~/.ssh/maxapoc_deploy_lab maxapoc-deploy@192.168.56.10 'deploy sha256:<digest>'
```
`IdentitiesOnly=yes` обязателен для проверок ключей: без него клиент предложит и другие ключи из агента, и тест «чужой ключ не пускают» будет ложным.

## 6. Откат

**Образ на шаг назад.** Деплой прошлого digest тем же путём — отдельной команды нет. Прошлый digest — в `release.env.prev`, образ уже на сервере (реестр не нужен).

**Глубже, чем на шаг.** Digest нужной версии: журнал сервера (`journalctl -t maxapoc-deploy-run` — каждая строка `deploy … OK` — версия, которая реально работала), сводки запусков `Proxy` в GitHub, страница пакета. Затем `deploy <digest>`; образ скачается из реестра.

> Откат прокси безопасен, только если прокси обратно совместим с выпущенными версиями приложения.

**Compose-файл** (его доставляет Ansible из `main`):
1. Срочно: `ansible-playbook -i inventory/prod site.yml -e maxapoc_repo_version=<хеш хорошего коммита>` — временно, сервер отличается от `main`, следующий обычный запуск вернёт плохой compose.
2. Закрепить: `git revert <плохой коммит>` → `dev` → `main` → обычный запуск Ansible.

**Изменение контракта** (новая переменная в `.env` и compose + код, который её использует) — два выпуска: сначала compose и `.env`, совместимые со старым образом (вливание + Ansible), потом код ([ADR-007](DECISIONS.md#adr-007)).

<a id="break-glass"></a>
## 7. Аварийный выпуск при недоступном реестре (break-glass)

Когда GHCR недоступен (или протух токен сервера), а исправление нужно сейчас. Ключ CI для этого не подходит и не должен: выполняется под личным пользователем с sudo, каждое `sudo` в журнале.

1. На машине с Docker, в рабочей копии MaxApoc, на коммите с исправлением: `cd proxy && node --test` (образ идёт мимо CI — тесты руками).
2. Сборка из корня репозитория: `docker build -f proxy/vps/Dockerfile -t maxapoc-proxy:breakglass-<коммит> proxy`.
3. Передача без файла: `docker save maxapoc-proxy:breakglass-<коммит> | ssh <пользователь>@<сервер> 'sudo docker load'`.
4. На сервере, в `/opt/maxapoc/proxy/vps`: сохранить текущий `release.env` в `release.env.prev`, записать `MAXAPOC_PROXY_IMAGE=maxapoc-proxy:breakglass-<коммит>` (у загруженного образа нет digest реестра — только тег).
5. `sudo docker compose --env-file .env --env-file release.env up -d --no-build --wait`.
6. Когда реестр вернётся: то же исправление обычным путём `dev` → `main` → деплой по digest; аварийный образ удалить (`docker image rm`).

## 8. Смена секретов

Секрет меняется в `vault.yml` своего окружения (`ansible-vault edit`) с последующим запуском плейбука для этого окружения.

| Секрет | Что сделать | Последствия |
|---|---|---|
| Токен Telegram-бота | новый токен у @BotFather (`/revoke` у старого) → vault → запуск | Alertmanager перезапустится сам; проверить тестовым алертом |
| Пароль Grafana | vault → запуск (контейнер Grafana должен работать) | роль меняет пароль командой `grafana cli admin reset-admin-password`; проверка: старый пароль `401`, новый `200` |
| Токен GitHub прокси (`GH_TOKEN`, `HUB_TOKEN`) | новый токен → vault → запуск → старый отозвать | контейнер пересоздаётся с новым `.env`; приложение не пересобирается |
| Ключ приложения `APP_KEY` | vault → запуск **и** секрет репозитория приложения → пересборка | установленные приложения со старым ключом перестанут работать с прокси |
| Ключи LLM-шлюзов | vault → запуск | контейнер пересоздаётся |
| Сертификат сервера (продление, смена адреса) | `make-certs.sh` вне сервера → vault → запуск | handler перезапускает прокси; при смене адреса — новый `PROXY_URL` и пересборка приложения |
| Токен реестра на сервере (`vault_maxapoc_proxy_registry_token`, classic PAT `read:packages`, 90 дней; напоминание за 7 дней) | новый токен → vault своего окружения → запуск → старый отозвать | без токена сервер не скачает новый образ (деплой — код 2), работающий прокси не затронут |
| Ключ деплоя (CI) | `ssh-keygen` нового ключа → публичная часть в `maxapoc_deploy_pubkey` инвентаря → запуск (старый ключ уходит, `exclusive`) → приватная часть в секрет окружения `DEPLOY_SSH_KEY` → ручной запуск `Proxy` с `main` (`deploy-check`) | у тестовой среды и рабочего сервера ключи разные |
| Ключ хоста сервера (переустановка) | новый отпечаток сверить **через консоль хостера** (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), затем строку в `DEPLOY_KNOWN_HOSTS` | до обновления деплой падает с кодом 255 — так и задумано |
| Пароль vault окружения | `ansible-vault rekey --vault-id <id>@<старый> --new-vault-id <id>@<новый> <файлы>`, затем заменить файл пароля | сначала перешифровать, потом заменять |

**Потеря пароля vault окружения.** Перешифровать без него нельзя. Нужно выпустить заново все секреты этого окружения (токены GitHub, ключи шлюзов, `APP_KEY` с пересборкой приложения, сертификат, токен бота, пароль Grafana) и создать новый `vault.yml`. Поэтому копия пароля в менеджере паролей обязательна.

**Пароль Grafana, изменённый в интерфейсе,** плейбук не заметит (файл пароля не меняется) — это дрейф. Исправляется повторной сменой через vault.

## 9. Частые проблемы

| Симптом | Причина и действие |
|---|---|
| `Incorrect sudo password` на первой задаче | неверно введён `BECOME password` (у окружений разные пароли) |
| `Host key verification failed` | адрес сервера сменился или сервер переустановлен → зайти по SSH вручную и сверить отпечаток ключа; не удалять запись `known_hosts` вслепую |
| `Decryption failed` у `vault.yml` | не тот файл пароля для метки vault (`…;lab` / `…;prod`) или файл заменён |
| `'…' is undefined` для секрета | `vault.yml` лежит не в `host_vars/<имя хоста>/` (имя папки должно совпадать с алиасом хоста) |
| таймаут при скачивании ключа Docker, образов, отправке в Telegram | нет доступа к внешнему источнику → `curl` с сервера; в тестовой среде — прокси через `proxy_env` |
| контейнер `Restarting (1)` / `unhealthy` | приложение падает при старте → `sudo docker logs <имя> --tail 30` (пример: `APP_KEY` короче 16 символов) |
| цель `down`, `connection refused` | процесс не слушает порт: проверить лог старта контейнера и какой образ запущен (`docker inspect --format '{{.Config.Image}}'`) |
| `curl … Expecting value` / `Failed to connect` к 9090, 9093, 3000 | не открыт SSH-туннель или он не пробрасывает этот порт → `ss -tlnp | grep ssh`; либо проверить прямо на сервере по `127.0.0.1` |
| нет сообщений в Telegram | `docker logs maxapoc-alertmanager --tail 30`: `timeout` — нет сети до Telegram, `401` — токен, `400 chat not found` — номер чата |
| `MAXAPOC_PROXY_IMAGE is not set` | compose запущен без файлов переменных → `--env-file .env --env-file release.env` |
| `Local modifications exist` на первой задаче | в клоне `~/.cache/infra-lab/APP_REPO` что-то правили руками → `git -C ~/.cache/infra-lab/APP_REPO checkout -- .` |

### Инцидент 28.10.2026: Prometheus соседнего стека не вернулся после перезапуска Docker

- **Что случилось.** Роль `docker` создала `daemon.json` и перезапустила демон. Все контейнеры вернулись, кроме `hobot-prometheus` (стек `hobot-metrics`).
- **Влияние.** ~16 минут без метрик `hobot-metrics`. Прокси и пользователи не затронуты.
- **Обнаружение.** По пустым панелям Grafana, а не по проверке плана: проверка «все контейнеры подняты» выполнялась на глаз.
- **Устранение.** `docker start hobot-prometheus`.
- **Причина.** Не установлена: контейнер остановлен штатно (код 0, без нехватки памяти), политика `unless-stopped`; после старта демон не предпринял попытки его запустить, журнал демона этого не объясняет.
- **Меры.** Сравнение списка контейнеров до и после в плане работ (раздел 3); `live-restore` ([ADR-011](DECISIONS.md#adr-011)) — перезапуск демона больше не останавливает контейнеры.
