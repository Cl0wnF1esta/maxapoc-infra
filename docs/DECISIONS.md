<a id="adr-001"></a>
## ADR-001. Конфигурация сервера как код

**Статус:** принято. Проверено на тестовой виртуальной машине (ВМ) с отката снимка; рабочий сервер переведён 28.10.2026.

**Контекст.** Сервер настраивался вручную: пакеты, файрвол, Docker и прокси ставились командами, обновление прокси — `rsync` + `docker compose up -d --build`. Политика ufw по умолчанию — «разрешить». Восстановить сервер после сбоя или передать проект другому человеку можно было только по памяти автора. Ресурсы ограничены: 1 ГБ RAM.

**Решение.** Описать сервер кодом на Ansible и разворачивать одной командой.

1. **Роли по зонам ответственности:** `common` (база), `security` (SSH и файрвол), `docker`, `backup` (резервные копии), `maxapoc_proxy` (приложение), `maxapoc_deploy_access` (доступ деплоя), `maxapoc_monitoring` (стек мониторинга). Переменные роли — с префиксом её имени. Роль общая для всех окружений, различия — только в данных инвентаря.
2. **Окружения различаются данными, а не кодом.** Значения по умолчанию — в `defaults` роли; адреса, порты, размер swap, прокси — в `host_vars` хоста. Код роли не знает имени окружения. Переменная, нужная нескольким ролям (имя общей сети), лежит в общих переменных, а не в `defaults` одной из ролей: иначе вторая роль работала бы «случайно», за счёт порядка ролей в плейбуке.
3. **Идемпотентность как требование.** Модули, описывающие состояние, вместо команд; где команды неизбежны — проверка текущего состояния перед действием (не «файл только что создан», а «файл размечен как swap»). Перезапуски — через handlers и только при изменениях.
4. **Поддерживаемая платформа объявлена явно:** на любой ОС, кроме Ubuntu 24.04, плейбук останавливается первой задачей с понятным сообщением.
5. **Вход Ansible — под отдельным пользователем с sudo по паролю,** не под root и не в группе `docker`.

**Альтернативы**
- *Shell-скрипты.* Проще начать, но идемпотентность и повторный запуск пришлось бы обрабатывать вручную в каждом месте.
- *Ручная настройка по инструкции.* Не проверяется автоматически и расходится с реальностью.
- *`synchronize` (rsync) для доставки файлов.* Отклонено: запускает `sudo` в отдельном соединении без возможности ввести пароль и по умолчанию отключает проверку ключа хоста (`verify_host: false`).
- *sudo без пароля.* Отклонено: украденный SSH-ключ сразу давал бы root.

**Последствия**
- (+) Сервер воспроизводится с нуля; изменения проходят через git.
- (+) Секреты не хранятся открытым текстом ни в репозитории, ни в выводе (см. [ADR-004](#adr-004)).
- (−) Ручная правка на сервере теперь — дрейф: следующий запуск либо вернёт состояние из кода, либо (для того, что роль не описывает) не заметит правку.
- (−) Роли только добавляют: удалённое из списка правило ufw или файл остаётся на сервере до ручного удаления.

**Как проверено**
- Каждая проверка — с отката тестовой ВМ на снимок «чистая ОС + пользователь + ключ».
- Чистая ВМ → рабочий сервер: 6 мин 26 с (04.11.2026, все роли, включая резервные копии; через прокси тестовой среды; образ прокси скачивается готовым), `failed=0`; повторный запуск `changed=0`.
- Прерванный запуск (swap-файл без разметки) — роль восстанавливается сама.
- Изменение одного файла кода → пересборка образа → следующий запуск `changed=0`.
- Отсутствие утечек: поиск выдуманных значений секретов в логе запуска с `--diff` и по репозиторию — пусто; положительный контроль на сервере — значения на месте.
- Рабочий сервер: после перевода повторный запуск `changed=0`.

<a id="adr-002"></a>
## ADR-002. Docker из официального репозитория, закреплённые версии

**Статус:** принято, применено к обоим окружениям.

**Контекст.** На рабочем сервере Docker стоял из официального репозитория (`docker-ce` 29.8.2 и связанные пакеты), но версии не удерживались: любое `apt upgrade` могло обновить демон и перезапустить все контейнеры.

**Решение**
- Репозиторий `download.docker.com` в формате deb822 с ключом `signed-by` (цепочка доверия apt проверяет подпись пакетов).
- Все связанные пакеты (`docker-ce`, `docker-ce-cli`, `containerd.io`, `buildx`, `compose`) ставятся одной транзакцией в версиях, как на рабочем сервере, и удерживаются (`hold`). Обновление — осознанное: поднять версии в `defaults` роли и разрешить изменение удержанных пакетов.
- Старый `docker.list` (появляется при установке по инструкции с сайта Docker) роль удаляет: иначе один репозиторий описан дважды.
- `docker-model-plugin` роль не ставит. На рабочем сервере он предустановлен хостером и не используется; не удаляем, это записанное расхождение окружений.

**Альтернативы**
- *Пакет `docker.io` из репозитория Ubuntu.* Отклонено: другие версии, чем на рабочем сервере.
- *Последняя версия без закрепления.* Отклонено: сервер перестаёт быть воспроизводимым, обновление происходит неуправляемо.

**Последствия**
- (+) Тестовая среда и рабочий сервер на одних и тех же версиях.
- (−) Обновления безопасности Docker не приходят сами; их нужно отслеживать и поднимать версии вручную.

**Как проверено:** `apt-mark showhold` на рабочем сервере после перевода — все пакеты Docker на удержании; `apt-get update` без ошибок и без предупреждений о дубле источника.

<a id="adr-003"></a>
## ADR-003. Docker обходит ufw: доступ ограничивается адресом публикации

**Статус:** принято, применено.

**Контекст.** Порты, опубликованные Docker (`ports:`), открываются правилами перенаправления в iptables мимо правил ufw. Эксперимент в тестовой среде: порт, опубликованный без адреса, доступен снаружи при закрытом в ufw порте. Декоративные правила `DENY` для 3000/9090 на рабочем сервере ничего не защищали.

**Решение**
- Сервисы, которые не должны быть публичными, публикуются только на конкретный адрес:
  - `127.0.0.1` — стек мониторинга этого репозитория, доступ через SSH-туннель;
  - адрес WireGuard — метрики прокси для стека `hobot-metrics`.
- Сервисам, которым достаточно сети Docker (метрики прокси для Prometheus этого стека), порт не публикуется вообще.
- Защищает адрес публикации, а не файрвол; правила ufw для таких портов не пишутся.

**Альтернативы**
- *Правила в цепочке `DOCKER-USER`.* Работают, но это второе место описания доступа, которое легко рассинхронизировать с ufw.
- *Отключить управление iptables у Docker.* Отклонено: ломает сеть контейнеров.

**Последствия**
- (+) Порт мониторинга без пароля недоступен из интернета независимо от ufw.
- (−) Каждый новый `ports:` нужно проверять на адрес; порт без адреса открыт всем.

**Как проверено:** `ss -tlnp` в тестовой среде — 9090, 9093, 3000, 9101 только на `127.0.0.1`; на рабочем сервере 9101 только на адресе WireGuard.

<a id="adr-004"></a>
## ADR-004. Секреты

**Статус:** принято, применено.

**Решение**
1. **Ansible Vault.** У каждого хоста зашифрованный `vault.yml` в git; переменные в нём с префиксом `vault_`, роли читают их через ссылки в открытом `vars.yml` — имена видны поиском, значения нет.
2. **Отдельный пароль для каждого окружения** (vault ID `test` и `prod`). Утечка пароля тестовой среды не раскрывает секреты рабочего сервера. Пароли — в файлах вне git (права `0600`) и в менеджере паролей.
3. **`no_log`** у всех задач с секретами: значения не попадают в вывод, в том числе при `--diff` и в будущих логах CI.
4. **Контейнерам секреты передаются файлами, где приложение это умеет** (токен Telegram для Alertmanager, пароль Grafana): права `0400`, владелец — пользователь процесса в контейнере. Файла нет в `docker inspect`, в окружении процессов и у дочерних процессов. Прокси пока читает секреты из `.env` (`root`, `0600`): перевод на файлы требует изменения приложения.
5. **Сверка секретов без раскрытия** — по хешам SHA-256 (короткие значения так не сравнивают: они перебираются).

**Альтернативы**
- *Один пароль vault на всё.* Отклонено: пароль тестовой среды лежит на учебной машине.
- *Секреты в переменных окружения контейнеров.* Видны в `docker inspect` и окружении всех процессов.
- *Внешнее хранилище (HashiCorp Vault и т. п.).* Избыточно для одного сервера.

**Последствия**
- (+) В репозитории только шифротекст.
- (−) Файлы паролей vault лежат открытым текстом: доступ к управляющей машине под пользователем владельца раскрывает оба пароля.
- (−) Потеря пароля окружения = перевыпуск всех его секретов (`rekey` требует старого пароля).
- (−) Секрет может утечь через само приложение: Alertmanager пишет в лог URL запроса к Telegram вместе с токеном при ошибке сети.

**Как проверено:** заголовки `vault.yml` — `$ANSIBLE_VAULT;1.2;AES256;test` и `…;prod`; проверка подключения секретов через `is defined` без вывода значений; `docker inspect` у Alertmanager и Grafana — в окружении только путь к файлу; хеши секретов рабочего сервера совпали с vault до перевода.

<a id="adr-005"></a>
## ADR-005. Окружения: отдельные инвентари

**Статус:** принято, применено.

**Контекст.** Пароль sudo Ansible спрашивает один раз на запуск, а хосты выполняются параллельно. Запуск без ограничения по привычке задел бы рабочий сервер вместе с тестовой средой. Отдельной настройки «запретить запуск без `--limit`» в `ansible-core` нет.

**Решение**
- Два инвентаря: `inventory/test` (по умолчанию в `ansible.cfg`) и `inventory/prod` (только явно, `-i inventory/prod`).
- Общие переменные — в `ansible/group_vars/all.yml` рядом с плейбуком: они подключаются к любому инвентарю без дублирования.
- В обоих инвентарях есть группа `maxapoc_servers`, на которую ссылается плейбук.

**Альтернативы**
- *Один инвентарь и `--limit`.* Защищает только дисциплина.
- *Проверка `ansible_limit` в начале плея.* Работает, но запуск «по умолчанию» всё равно смотрел бы на оба окружения.

**Последствия**
- (+) Рабочий сервер нельзя задеть, не указав его инвентарь.
- (−) Общие переменные живут вне инвентаря; это нужно знать при чтении.

**Как проверено:** `ansible-inventory --graph` без `-i` показывает только тестовую среду, с `-i inventory/prod` — только рабочий сервер; после переноса файлов тестовая среда даёт `changed=0`.

<a id="adr-006"></a>
## ADR-006. Обособленный стек мониторинга проекта; на рабочем сервере пока выключен

**Статус:** принято. Стек проверен в тестовой среде; на рабочем сервере выключен переключателем `maxapoc_monitoring_enabled: false`.

**Контекст.** Метрики и оповещения MaxApoc на рабочем сервере сейчас обслуживает стек `hobot-metrics` (личный проект автора): файлы MaxApoc подкладываются в его каталог. Инфраструктура проекта должна описываться без привязки к чужим сервисам. При этом на рабочем сервере 1 ГБ памяти: по разведке доступно ~300 МБ, swap занят на ~400 МБ, а Grafana этого стека в тестовой среде занимает ~300 МБ.

**Решение**
- **Роль `maxapoc_monitoring`:**
  - Prometheus, Alertmanager, Grafana в общей сети с прокси;
  - правила и панели — из `observability/` проекта;
  - интерфейсы на `127.0.0.1`, доступ через SSH-туннель;
  - закреплённые версии образов, лимиты памяти;
  - проверка здоровья по HTTP в конце роли.
- Alertmanager — отдельный контейнер, не встроенный в Grafana: встроенный Alertmanager Grafana не принимает алерты от внешнего Prometheus, и доставка не должна зависеть от Grafana.
- На рабочем сервере роль выключена до появления второго сервера или тарифа с большей памятью. Метрики прокси для `hobot-metrics` публикуются на адресе WireGuard.

**Альтернативы**
- *Полный стек на рабочем сервере сейчас.* Отклонено по памяти.
- *Только Prometheus и Alertmanager, панели в Grafana `hobot-metrics`.* Сохраняет зависимость от чужого стека для просмотра.

**Последствия**
- (+) Стек проекта готов и проверен; включение — одна переменная.
- (−) На рабочем сервере наблюдаемость MaxApoc по-прежнему зависит от `hobot-metrics`; порт 9101 остаётся опубликованным на адресе WireGuard.

**Как проверено (тестовая среда):** цель `maxapoc-proxy` `up`; 20 правил загружено; тестовый алерт и учения с остановкой прокси — 🔴 через ~3,5 минуты, 🟢 после восстановления; источник данных и две панели Grafana через provisioning; смена пароля Grafana через vault (старый `401`, новый `200`); проверка здоровья по HTTP останавливает запуск, если сервис не поднялся.

<a id="adr-007"></a>
## ADR-007. Граница Ansible и деплоя

**Статус:** принято; рабочий сервер — 02.11.2026. Решение уточнено при реализации: compose-файл, правила и панели остались за Ansible (см. «Отступление от первоначального решения»).

**Контекст.** Состояние сервера меняется редко, версия приложения — часто. Если смешать, либо каждый деплой гоняет весь плейбук с доступом ко всему серверу, либо сервер меняют «по-быстрому» мимо кода.

**Решение**

| Что | Владелец | Как |
|---|---|---|
| ОС, защита, Docker, каталоги, общая сеть, пользователь деплоя | Ansible | роли `common`, `security`, `docker`, `maxapoc_deploy_access` |
| `.env` (секреты и окружение), сертификаты, `gateways.json` | Ansible | из vault и из чистого клона `main` ([ADR-019](#adr-019)) |
| `docker-compose.yml` прокси, правила оповещений и панели | Ansible | из чистого клона `main` ([ADR-019](#adr-019)) |
| Первоначальный `release.env` (только на сервере, где его нет) | Ansible | из последней резервной копии окружения; нет копии — `maxapoc_proxy_image` из инвентаря ([ADR-017](#adr-017)) |
| **Версия образа** (`release.env`) | **деплой из CI** | `deploy <digest>` через ограниченный ключ ([ADR-016](#adr-016), [ADR-017](#adr-017)) |
| Данные Prometheus, тишины Alertmanager, база Grafana | сам сервис | в репозитории их нет → резервные копии ([ADR-023](#adr-023)) |

- **Стык — контракт имён:**
  - переменные `.env`;
  - путь к `release.env`;
  - пути к сертификатам;
  - имя сети.
- **Изменение контракта — в два шага.** Сначала compose и `.env`, совместимые со **старым** образом (вливание в `main` + запуск Ansible), затем код, который их использует. Одним коммитом нельзя: вливание в `main` сразу запускает деплой, а Ansible в этот момент ещё не запущен. Если всё же влить одним коммитом, новый код без переменной не станет healthy, и деплой откатится сам ([ADR-018](#adr-018)).
- **CI деплоя не знает секретов приложения:** ему нужны только ключ деплоя, адрес сервера и `known_hosts`.
- **Чистый сервер:** Ansible берёт версию из последней копии окружения, а без копии — начальную из инвентаря; затем первый деплой приносит актуальную. Проверено: чистая ВМ → один запуск (6 мин 05 с) → деплой (1 мин 09 с — до ускорения проверки здоровья, сейчас ~7 с) → повторный запуск `changed=0`; версия из копии — удалением `release.env` в тестовой среде.

**Отступление от первоначального решения.** Изначально compose-файл, правила и панели должны были ехать «вместе с релизом». Это потребовало бы либо передавать файл конфигурации через ключ CI (ключ смог бы менять порты, тома и привилегии контейнера — отклонено), либо доставать compose из образа при каждом деплое (лишний код). Compose меняется редко, поэтому он остался за Ansible, но источник — только `main` ([ADR-019](#adr-019)). Цена — правило двух шагов выше; рассинхрон «откат образа без отката compose» возможен, если не соблюдать совместимость.

**Последствия**
- (+) Утечка из CI не раскрывает секреты приложения; ключ CI не меняет конфигурацию запуска.
- (+) Ansible не перетягивает версию у деплоя: повторный запуск после деплоя — `changed=0` (проверено).
- (−) Два владельца у одного каталога на сервере; граница держится на `force: false` и правиле двух шагов.

<a id="adr-008"></a>
## ADR-008. `gateways.json` — конфигурация приложения

**Статус:** принято, применено.

**Контекст.** Файл задаёт порядок LLM-шлюзов, суточные потолки и параметры отключения маршрутов. Еженедельный workflow `gateway-bench` (по понедельникам и вручную) прогоняет маршруты из `proxy/vps/gateways.example.json` и кладёт предложенный порядок (`gateways.suggested.json`) и таблицу результатов в сводку запуска и артефакт. В репозиторий и на сервер он ничего не пишет (права workflow — только чтение). Раньше предложенный файл предполагалось вручную класть на сервер. На рабочем сервере стоял файл, совпадающий с `gateways.example.json`. Ключей в файле нет, только имена переменных.

**Решение.** Источник истины — `proxy/vps/gateways.example.json` в репозитории проекта.

1. Владелец смотрит артефакт замера и, если согласен, переносит изменения в `gateways.example.json` (сверяя `limits`, чтобы их не потерять) и коммитит.
2. Файл доставляется на сервер как `gateways.json` ролью `maxapoc_proxy` из чистого клона `main` ([ADR-019](#adr-019)).
3. Ручные правки на сервере не делаются.

**Альтернативы**
- *Файл хоста в инвентаре.* Отклонено: вторая копия, которая разойдётся с проектом.
- *Не трогать существующий файл и править руками.* Отклонено: правильная версия существовала бы только на сервере, без истории и вне резервных копий.

**Последствия**
- (+) У каждого изменения порядка шлюзов и потолков есть история в git.
- (−) Изменить потолки «на лету» на сервере нельзя — только через репозиторий и запуск доставки.
- (−) Файл подключён в контейнер отдельным файлом (bind mount файла). Ansible записывает новый файл через переименование, и работающий контейнер продолжает видеть старый (проверено в тестовой среде: хеши на хосте и в контейнере разошлись). Поэтому изменение `gateways.json` перезапускает прокси (короткий перерыв). Подключение каталога вместо файла — не сделано, остаётся улучшением.
- (−) Имя `…example.json` вводит в заблуждение: это рабочая конфигурация. Инструкцию в SETUP.md проекта («положите файл в `proxy/vps/gateways.json` на сервере») нужно привести в соответствие с этим решением.

<a id="adr-009"></a>
## ADR-009. Файрвол рабочего сервера

**Статус:** принято, применено 28.10.2026.

**Контекст.** До перевода: ufw `default allow incoming`, правила `22 ALLOW`, `51820/udp`, `8443`, декоративные `DENY` для 3000/9090. Наружу слушали также xray (входящие порты в диапазоне), панель и подписка x-ui, агент Zabbix хостера.

**Решение**
- `default deny` для входящих; политика `routed` не меняется (WireGuard).
- SSH — отдельной задачей с `LIMIT` (6 подключений за 30 с с одного адреса).
- Остальные порты — списком в инвентаре, с назначением в комментарии правила:
  - 8443 — прокси;
  - 51820/udp — WireGuard;
  - `33000:38000` — входящие xray (диапазон в коде, конкретные порты — в панели);
  - 2096 — подписка x-ui;
  - 4467 — панель x-ui;
  - 10050 — только с трёх адресов Zabbix хостера.
- Старые правила удаляются вручную после перевода (роль только добавляет). Существующее `22 ALLOW` ufw при добавлении `limit` обновил на месте.

**Принятый риск:** панель x-ui открыта в интернет (случайный путь, сложный пароль, TLS).

**Альтернативы**
- *`ALLOW` вместо `LIMIT` на 22 «для CI».* Отклонено по замеру: деплой делает **одно** SSH-подключение за запуск, `LIMIT` (6 за 30 с) ему не мешает.

**Как проверено:** разведка `ss -tulpn` до перевода — всё, что слушает наружу, есть в списке; после перевода `ufw status verbose` — `deny (incoming)`, список совпадает с кодом; xray, WireGuard, Zabbix, приложение работают.

<a id="adr-010"></a>
## ADR-010. Перевод работающего прокси на Ansible

**Статус:** принято, выполнено 28.10.2026.

**Контекст.** Прокси работал из `/root/maxapoc-proxy/vps` (compose-проект `vps`), от root (`PROXY_UID=0`), образ `vps-maxapoc-proxy:latest` собирался на сервере. Роль разворачивает его в `/opt/maxapoc/proxy/vps`, процесс от uid 1000.

**Решение**
1. **Сверка до перевода:** секреты, имена репозиториев и отпечатки сертификатов — по хешам с vault (совпали); код — по хешам файлов (отличался только `docker-compose.yml`). Перевод не меняет версию приложения.
2. **Репетиция в тестовой среде** с копией «как на рабочем сервере» (тот же каталог, root, старый код).
3. **Своё имя образа `maxapoc-proxy:local`.** Репетиция показала: у старого и нового каталогов одно имя compose-проекта, значит, и одно имя образа. Роль взяла образ, собранный старым каталогом, а откат вернул бы конфиг, но не код.
4. **Порядок:** роль пересоздаёт контейнер (compose «усыновляет» старый контейнер по имени проекта), простой ~1 с на пересоздание.
5. **Откат** одной строкой: `docker compose -f /opt/... down && docker compose -f /root/maxapoc-proxy/vps/docker-compose.yml up -d` (1–2 с); старый образ помечен `pre-ansible`.
6. **Уборка** через 1–2 недели — без `docker compose down` из старого каталога: из-за общего имени проекта он остановил бы текущий прокси.

**Последствия**
- (+) Прокси работает не от root.
- (−) Решение о пересборке образа по изменению доставленных файлов не видело, что образ под тем же именем подменил кто-то другой. **Закрыто:** образ собирается в CI и запускается по digest ([ADR-015](#adr-015)); сборка на сервере снята ([ADR-020](#adr-020)).

**Как проверено:** репетиция (пересоздание без ошибки, простой ~1 с, uid 1000, откат); на рабочем сервере — `maxapoc-proxy:local`, `healthy`, uid 1000, без ошибок прав, суммарный простой 4 с, метрики в Grafana `hobot-metrics`, запросы приложения и хаб работают.

<a id="adr-011"></a>
## ADR-011. `live-restore` демона Docker

**Статус:** принято. Тестовая среда — включено и проверено; рабочий сервер — 30.10.2026, без перезапуска контейнеров.

**Контекст.** При переводе рабочего сервера роль `docker` создала `daemon.json` и перезапустила демон. Все контейнеры вернулись, кроме Prometheus соседнего стека `hobot-metrics` (политика `unless-stopped`, штатная остановка, без нехватки памяти): демон после старта не предпринял попытки его запустить, журнал этого не объясняет. ~16 минут без метрик, обнаружено по пустым панелям.

**Решение.** `"live-restore": true` в `daemon.json` (роль `docker`, переменная `docker_live_restore`): контейнеры продолжают работать, пока демон перезапускается.

**Последствия**
- (+) Перезапуск демона больше не останавливает контейнеры — класс сбоев исчезает независимо от причины инцидента.
- Включение не требует перезапуска демона: `live-restore` применяется перечитыванием конфигурации (`systemctl reload docker`). На рабочем сервере `daemon.json` записан вручную ровно как шаблон роли, проверен `dockerd --validate`, применён reload; затем роль увидела совпадающий файл и демон не перезапускала.

**Как проверено:** в тестовой среде `docker info` → `LiveRestoreEnabled: true`; `systemctl restart docker` — время старта и счётчик перезапусков всех контейнеров до и через 2 минуты после совпали. Рабочий сервер (30.10.2026): после reload `LiveRestoreEnabled: true`, время старта и счётчики всех контейнеров не изменились; предпросмотр Ansible больше не показывает перезапуск Docker.

<a id="adr-012"></a>
## ADR-012. Внешние зависимости

**Статус:** принято, применено.

**Контекст.** Развёртывание зависит от зеркал Ubuntu, репозитория Docker, Docker Hub, GitHub, Telegram — они могут стать недоступны без изменений с нашей стороны. Из сети тестовой среды `download.docker.com`, Docker Hub и Telegram напрямую недоступны.

**Решение**
- Сетевые задачи повторяются несколько раз, затем запуск останавливается с ошибкой.
- Тестовая среда ходит через HTTP-прокси управляющей машины, открытый только для сети тестовой среды. Каждый, кому нужен прокси, получает его явно:
  - задачи Ansible — `environment:`;
  - демон Docker — `daemon.json`;
  - Alertmanager — `proxy_url` получателя.

  Процессы в контейнерах о прокси сами не знают.
- У рабочего сервера прокси нет.

## ADR-014. Закрытый ключ CA прокси вне сервера

**Статус:** принято, выполнено.

**Контекст.** Приложение доверяет только сертификатам, подписанным CA проекта. `ca.key` хранился на рабочем сервере.

**Решение.** `ca.key` вынесен в менеджер паролей владельца (у базы менеджера есть копия на втором компьютере) и удалён с сервера; резервные копии хостера, сделанные до выноса, удалены. Сертификат сервера выпускается вне сервера и доставляется через vault.

**Принятый риск:** CA не перевыпускался — признаков компрометации нет, а перевыпуск требует пересборки приложения у всех пользователей.

<a id="adr-015"></a>
## ADR-015. Образ прокси собирается в CI, сервер скачивает его по digest

**Статус:** принято. Тестовая среда — 29.10.2026, рабочий сервер — 02.11.2026.

**Контекст.** Образ собирался на сервере (1 ГБ RAM) из файлов на диске под одним именем `maxapoc-proxy:local`. Имя можно перезаписать новой сборкой, поэтому «откат на прошлый образ» не гарантировал прошлый код ([ADR-010](#adr-010)).

**Решение**
- **Задача `image`** в workflow `Proxy` (после тестов):
  - собирает образ и публикует его в приватный GHCR: `ghcr.io/cl0wnf1esta/maxapoc-proxy:sha-<коммит>`;
  - метки `org.opencontainers.image.source` и `revision`;
  - права задачи — только `contents: read` и `packages: write`; токен — временный `GITHUB_TOKEN`.
- Задача отдаёт **digest** (`sha256:…`) — неизменную ссылку на содержимое. Сервер запускает образ только по digest (`имя@sha256:…`), не по тегу: тег перезаписывается повторным запуском сборки, digest — нет.
- Сервер входит в реестр токеном **только на чтение** (classic PAT `read:packages`, 90 дней); у тестовой среды и рабочего сервера **разные** токены (в vault своего окружения).

**Альтернативы**
- *Деплой по тегу `sha-<коммит>`.* Отклонено: повторный запуск сборки перезаписывает тег новым digest (наблюдалось: три запуска на одном коммите — три digest).
- *Fine-grained токен на один репозиторий.* Недоступен: GitHub Packages принимает только classic-токены.
- *Deploy key репозитория.* Не подходит: даёт доступ к git по SSH, реестр принимает только токены.
- *Отдельный «машинный» аккаунт GitHub с доступом только к пакету.* Отложено (см. последствия).

**Последствия**
- (+) Один и тот же проверенный образ (тот же digest) едет на любой сервер; откат на digest возвращает ровно прошлое содержимое.
- (+) Сервер не тратит память и время на сборку: чистая ВМ поднимается за 6 мин 05 с вместо 15 мин 25 с (одинаковый состав ролей, без резервных копий; с ними — 6 мин 26 с).
- (−) Classic-токен читает все пакеты аккаунта (сейчас пакет один). Улучшение — машинный аккаунт с доступом только к пакету.
- (−) Токен хранится на сервере в `/root/.docker/config.json` (`0600`, base64 — не шифрование). Срок 90 дней — напоминание в менеджере паролей за 7 дней; протухший токен ломает только скачивание нового образа, не работающий прокси.
- (−) Пересборка того же коммита даёт другой digest (время сборки, передвигаемый базовый образ `node:22-alpine`).

**Как проверено:** метка `revision` образа совпадает с коммитом; пакет приватный и привязан к репозиторию; сервер запускает `…@sha256:…` и `healthy`; `/root/.docker/config.json` — `root`, `0600`.

<a id="adr-016"></a>
## ADR-016. Доступ CI к серверу

**Статус:** принято. Тестовая среда и рабочий сервер — 30.10.2026.

**Контекст.** CI должен выкатывать новую версию, но утечка того, чем он для этого пользуется, не должна давать доступ к серверу.

**Решение**
- **Отдельный пользователь `maxapoc-deploy`** (роль `maxapoc_deploy_access`):
  - пароль заблокирован;
  - не в группе `docker`;
  - без общего sudo.
- **Ключ с ограничениями** в `authorized_keys`:
  - `restrict` — без терминала, пробросов, агента;
  - `command="/usr/local/bin/maxapoc-deploy-gate"` — что бы ни попросил клиент, запускается этот скрипт;
  - в файле только этот ключ (`exclusive`);
  - отдельные ключи у тестовой среды и рабочего сервера.
- **Скрипт-фильтр** (`root`, `0755`):
  - пропускает только `status` и `deploy sha256:<64 символа 0-9a-f>` (шаблон на строку целиком);
  - пишет в журнал (`logger -t maxapoc-deploy-gate`) адрес клиента и решение;
  - непроверенный ввод в журнал пишется экранированным (`printf '%q'`), чтобы перевод строки не подделал запись.
- **sudo на один скрипт:**
  - `/etc/sudoers.d/maxapoc-deploy` (`0440`, проверка `visudo -cf`) разрешает без пароля только `/usr/local/sbin/maxapoc-deploy-run`;
  - скрипт — `root`, `0700`: пользователь деплоя не может его ни изменить, ни прочитать;
  - скрипт сам ещё раз проверяет формат, имя образа зашито в нём.
- **Окружение GitHub `production`:**
  - правило веток — только `main`;
  - `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_KNOWN_HOSTS` — секреты окружения, не репозитория;
  - задача с другой ветки отклоняется до запуска шагов, секреты ей не выдаются.
- **Ключ хоста — по доверенному каналу:**
  - строка `known_hosts` прочитана с сервера через уже проверенное SSH-подключение, отпечаток сверен;
  - в CI `StrictHostKeyChecking=yes`, без `ssh-keyscan`.

**Альтернативы**
- *Секреты приложения в CI (пароль vault или хранилище секретов).* Отклонено: код workflow, получивший секрет, может его передать наружу; деплою секреты приложения не нужны вообще.
- *CI передаёт compose-файл на сервер.* Отклонено: ключ CI смог бы задать `privileged`, тома и порты, то есть получить root.
- *Self-hosted runner в тестовой среде* (чтобы CI доставал до неё за NAT). Отклонено: на управляющей машине лежат пароли vault; логика деплоя отрабатывается в тестовой среде вручную теми же командами.
- *`ALLOW` вместо `LIMIT` на порт 22.* Не нужно: одно SSH-подключение за деплой ([ADR-009](#adr-009)).

**Последствия**
- (+) С украденным ключом CI можно только узнать статус и выкатить образ из нашего реестра; оболочки, чтения `.env` и сертификатов нет.
- (−) Ключ CI защищает связь «репозиторий → сервер», но не то, что попало в `main`: кто может запушить в `main`, тот управляет продом. Защита `main` — доступ к аккаунту (2FA); защита веток для приватного репозитория — только на платном тарифе.
- (−) При смене ключа хоста сервера деплой падает (правильно); новый отпечаток сверяется через консоль хостера, не через SSH.

**Как проверено:** `status` — образ и `healthy`; вход без команды — нет терминала и `denied`; `status; id`, короткий digest и digest с переводом строки — `denied`, код 1; проброс порта `-R` — отклонён; ключ тестовой среды на рабочем сервере с `IdentitiesOnly=yes` — отказ; `sudo -l` — одна команда; задача `deploy-check` с ветки — отклонена окружением, с временно разрешённой веткой — `healthy`, секреты в логе `***`, после снятия правила — снова отказ.

<a id="adr-017"></a>
## ADR-017. Версия образа — в `release.env`, владелец — деплой

**Статус:** принято. Тестовая среда — 30.10.2026, рабочий сервер — 02.11.2026.

**Контекст.** Если версия лежит в `.env`, который пишет Ansible, то любой запуск плейбука после деплоя тихо вернёт версию из инвентаря — с видимостью успеха.

**Решение**
- Переменная `MAXAPOC_PROXY_IMAGE` живёт только в `release.env`. Его пишет скрипт деплоя; Ansible создаёт файл **только если его нет** (`force: false`) и больше не трогает.
- **Сервер без `release.env`** (чистый или файл потерян):
  - сначала — версия из последней копии этого окружения (`restic restore … --include …/release.env`; роль `backup` идёт раньше роли прокси);
  - не вышло — начальная версия из инвентаря, с предупреждением в выводе;
  - задача выполняется только при отсутствии файла (`creates:`).
- Compose читает оба файла: `--env-file .env --env-file release.env` (у Ansible — `env_files`, в том числе в обработчике перезапуска). `release.env` не подключается в окружение контейнера.
- В compose: `image: "${MAXAPOC_PROXY_IMAGE:?…}"` — без файла версии compose останавливается с подсказкой, а не подставляет значение по умолчанию.

**Последствия**
- (+) Повторный запуск Ansible после деплоя — `changed=0`, версия не откатывается (проверено ручной записью «деплоя» в `release.env`).
- (+) Ручной `docker compose` без `--env-file` падает громко, а не запускает другую версию.
- (−) Значение `maxapoc_proxy_image` в инвентаре — запасная начальная версия (когда копии нет), не «что сейчас работает» (смотреть `status`). Оно должно быть свежим и совместимым с текущим compose.
- (−) Связь ролей: роль прокси пользуется обёрткой restic из роли `backup`; без копий — запасной путь.
- Из копии приходит версия, работавшая на момент последней копии (≤ суток), а не перед потерей файла.
- Ansible не хранит состояние между запусками; потерянный `release.env` возвращается из копии ([ADR-024](#adr-024)), без копии — начальная версия.

**Как проверено:** удалённый `release.env` восстановлен из копии (в файле — версия из снимка, не из инвентаря), прокси `healthy`; при выключенных копиях — начальная версия из инвентаря; переменной версии нет ни в `.env`, ни в окружении контейнера; `docker compose config` без `--env-file` — ошибка с подсказкой; пересборка с нуля нашла обработчик без `env_files` — исправлено и проверено повторной пересборкой.

<a id="adr-018"></a>
## ADR-018. Скрипт деплоя: скачать до переключения, ждать healthy, откатить

**Статус:** принято. Проверено в тестовой среде, в том числе намеренно сломанным образом; на рабочем сервере — каждым деплоем из CI с 02.11.2026.

**Решение** (`maxapoc-deploy-run deploy <digest>`, под блокировкой `flock` — второй деплой получает отказ, а не очередь):
1. `docker pull` нового образа. Не скачался — выход, на сервере ничего не изменилось (код 2).
2. Текущая версия копируется в `release.env.prev`.
3. Новая версия пишется атомарно (временный файл + `mv`).
4. `docker compose up --no-build --wait --wait-timeout 60`. Healthy — `OK`, затем удаляются образы реестра, кроме текущего и предыдущего (код 0).
5. Не healthy за 60 с — `release.env.prev` возвращается, `up --wait` на прошлую версию (код 4); если и это не удалось — код 5.

В CI коды превращаются в аннотации (`::error::…`); задача `deploy` идёт только по `push` в `main`, с `concurrency` без отмены (обрыв SSH посреди деплоя опаснее ожидания) и проверкой, что коммит есть в истории `main`.

**Проверка здоровья прокси:** `start_period: 30s`, `start_interval: 2s` (при `interval: 60s`, `retries: 3`) — в начале частые проверки, первая удачная сразу даёт healthy. Таймаут ожидания согласован со `start_period`, а не со временем объявления `unhealthy` (~210 с): версия, которой нужно больше минуты, считается сломанной.

**Альтернативы**
- *Отдельная команда «откат» и тег `stable`.* Отклонено: тег — передвигаемый указатель; второй путь кода запускался бы только в аварию. Откат — это деплой прошлого digest тем же путём.
- *Blue-green (два экземпляра и переключатель трафика).* Отклонено по цене: память (1 ГБ) и сложность при одном пользователе. Цена — простой ~1 с на пересоздание и до 60 с работы сломанной версии до отката.
- *`docker image prune -a`.* Запрещено на сервере: удалит предыдущий образ, на который опирается откат без реестра.

**Последствия**
- (+) Протухший токен или недоступный реестр ломают деплой **до** остановки старой версии.
- (+) Откат на шаг назад не зависит от реестра и сети.
- (−) `release.env.prev` хранит один шаг; после отката он равен текущему. Глубже — деплой старого digest из журнала `maxapoc-deploy-run` или сводки CI.
- (−) Слишком короткий таймаут при нехватке памяти даст ложный откат исправной версии.

**Как проверено:** несуществующий digest — код 2, версия прежняя; деплой — `OK`, `.prev` = прошлая версия; время подтверждения в тестовой среде 1 мин 08 с → 6,4 с, на рабочем сервере 7 с (03.11.2026); образ, у которого процесс работает, а проверка здоровья всегда падает (опубликован ручным запуском с отдельной ветки, на прод попасть не мог), — через 60 с откат, healthy на прошлой версии за 4 с, код 4, всего 1 мин 10 с; сломанный образ удалён следующим успешным деплоем; на рабочем сервере после деплоя из 4 образов осталось 2.

<a id="adr-019"></a>
## ADR-019. Источник файлов для серверов — чистый клон `main`

**Статус:** принято, применено 02.11.2026.

**Контекст.** Роли брали compose, `gateways.json` и наблюдаемость из рабочей копии MaxApoc на диске — с той ветки, что открыта. Экспериментальная правка могла уйти на рабочий сервер в обход CI.

**Решение.** Первая задача плейбука (`pre_tasks`, на управляющей машине, один раз, без sudo) обновляет отдельный клон `~/.cache/infra-lab/APP_REPO` до ветки `main` (`ansible.builtin.git`, `force: false`). Пути `maxapoc_proxy_src` и `maxapoc_monitoring_stack_src` указывают в этот клон. Ручные правки в клоне — громкая ошибка до всех ролей.

**Последствия**
- (+) На серверы попадает только то, что прошло `main`.
- (−) Клон общий для окружений: рабочий сервер получает `main` на момент своего запуска, а не на момент проверки в тестовой среде. Чтобы получить ровно проверенное — `-e maxapoc_repo_version=<хеш коммита>`.
- (−) Срочный откат compose: `-e maxapoc_repo_version=<хеш>` (временно, сервер ≠ `main`), затем `git revert` по обычному потоку.

**Как проверено:** экспериментальная правка compose в рабочей копии на отдельной ветке — `changed=0`; правка в клоне — ошибка `Local modifications exist`, плей остановлен до ролей.

<a id="adr-020"></a>
## ADR-020. Снят запасной режим сборки на сервере

**Статус:** принято, выполнено 02.11.2026 (после двух деплоев из CI на рабочий сервер).

**Решение.** Удалены переключатель `maxapoc_proxy_build_on_server`, файл задач сборки, список файлов кода и условия в роли; compose запускается с `build: never`, `pull: missing`. На обоих серверах удалены файлы кода и образ `maxapoc-proxy:local`.

**Почему.** Невыполняемый путь ломается незаметно и подводит именно тогда, когда нужен. Один проверенный путь доставки надёжнее двух.

**Последствия**
- (−) При недоступном реестре новую версию выкатить нельзя. Аварийный порядок (break-glass) — в [OPERATIONS](OPERATIONS.md#break-glass).

**Как проверено:** деплой в тестовую среду без файлов кода — `OK`; повторные запуски на обоих серверах — `changed=0`.

<a id="adr-021"></a>
## ADR-021. Приложение и прокси — в одном репозитории; поток `dev` → `main`

**Статус:** принято.

**Контекст.** `main` — ветка выпусков приложения, и слияние в неё же выкатывает прокси. Рассматривался вынос прокси в отдельный репозиторий.

**Решение.** Оставить один репозиторий. Изменение протокола между приложением и прокси делается одним коммитом. Все изменения идут `dev` (проверки) → `main` (выпуск; для прокси — автодеплой). Сборку APK изменения только в `proxy/**`, `observability/**`, `proxy.yml` не запускают (`paths-ignore`), изменения `observability/**` не пересобирают образ прокси.

**Последствия**
- (+) Нет второго репозитория, второго окружения и согласования версий между ними.
- (−) В `dev` попадает только то, что можно выкатить: прокси уходит на прод при ближайшем слиянии.
- (−) Прокси выкатывается сразу, а приложение у пользователя обновляется когда угодно → прокси обязан быть обратно совместим с выпущенными версиями приложения (иначе и откат прокси небезопасен).
- Исключение: если в `dev` лежит то, что выпускать нельзя, срочное исправление прокси — ветка от `main` → `main`, затем `main` → `dev`.

**Как проверено:** первый деплой из CI (02.11.2026): `main` перемотан на `dev`, Build APK на время вливания выключен (до добавления `observability/**` в исключения) и включён обратно; выпуск приложения не создан.

<a id="adr-022"></a>
## ADR-022. Проверка после деплоя — процесс, а не код

**Статус:** принято (принятый риск).

**Контекст.** Деплой проверяет только healthy при старте. Сбой через несколько минут после healthy он не ловит. CI не имеет доступа к Prometheus рабочего сервера.

**Решение.** После деплоя — 15 минут смотреть оповещения и панель прокси ([OPERATIONS](OPERATIONS.md#deploy)). Повторная проверка из CI и запросы к Prometheus не делаются. Ручной запуск workflow только читает (`deploy-check`), выкатывает только `push` в `main`.

**Обоснование.** Один разработчик и один пользователь; время выкладки выбирает тот же человек; неудачный выпуск не несёт репутационных и финансовых рисков. Новый путь доступа CI внутрь и код повторной проверки дороже риска.

**Последствия.** Поздний сбой обнаруживается оповещениями `MaxapocServerErrors` / `MaxapocProxyDown` в Prometheus стека `hobot-metrics` (правила загружены, проверено 03.11.2026) примерно через 11–20 минут; ночью реакция — часы. Правила прокси существуют в двух местах (`observability/` в MaxApoc и копия в `hobot-metrics`) — синхронизируются вручную.

**Пересмотреть, если:** выпуски делает не только владелец; у продукта появляются реальные пользователи; появляются обязательства по доступности.

<a id="adr-023"></a>
## ADR-023. Резервные копии: restic в S3 хостера и ежемесячная копия домой

**Статус:** принято. Тестовая среда и рабочий сервер — 04.11.2026.

**Решение**
- **Роль `backup`:**
  - restic, ежедневно по таймеру systemd (`03:30` + до 30 мин, `Persistent=true`) в приватный бакет S3 хостера (стандартный класс);
  - у каждого окружения свой репозиторий (префикс `test/`, `prod/`) и свой пароль;
  - пароль и ключи S3 — в vault окружения, пароль ещё и в менеджере паролей.
- Хранение: 7 ежедневных, 4 еженедельных, 6 ежемесячных снимков (`forget --prune`); по воскресеньям `restic check`.
- Сбой копии → `OnFailure=` → сообщение в Telegram (бот и чат окружения).
- Раз в месяц вручную с управляющей машины: `restic copy` из S3 в локальный репозиторий (`--copy-chunker-params`), очистка и проверка там же ([OPERATIONS](OPERATIONS.md#backup)).

**Альтернативы**
- *Холодный класс хранения.* Отклонено: restic при каждой копии читает индекс, `forget`/`prune` удаляют; у холодных классов минимальный срок хранения, плата за чтение, иногда «разморозка». При ~20 МБ экономии нет.
- *Снимки диска у хостера.* Не замена: копия «как при выдернутом питании» (база SQLite в режиме WAL может быть несогласованной) и тот же аккаунт.
- *Забирать копию домой автоматически (pull).* Отложено: ещё один пользователь и фильтр на сервере; домашний компьютер включён не всегда.

**Последствия**
- (+) Потеря VPS — восстановление из S3 с потерей до суток; потеря аккаунта хостера — из домашней копии с потерей до месяца.
- (+) Объём: 16,8 МиБ данных рабочего сервера занимают в хранилище 3,5 МиБ (сжатие); копия — ~10 с.
- (−) Ключ S3 один на бакет (хостер не выдаёт других): тестовая среда может удалить копии рабочего сервера, но не расшифровать (пароли разные).
- (−) Root на рабочем сервере = пароль и ключи копий: чтение, удаление, подмена. Отставание защищённой копии — до месяца (домашняя).
- (−) Ежемесячная копия домой держится на человеке. Улучшение — таймер пользователя на управляющей машине.
- (−) Выключенный таймер оповещением не ловится (ловится только упавшая копия).

**Как проверено:** копия через службу; без файла пароля служба упала, оповещение пришло само; восстановленные базы x-ui и Grafana — `integrity_check ok`, в x-ui 3 inbound-а; копия домой и восстановление из неё — `ok`.

<a id="adr-024"></a>
## ADR-024. Копируется состояние, а не код

**Решение.** Копируется только то, что нельзя воссоздать из git, vault и реестра образов:

| Что | Почему |
|---|---|
| база x-ui (пользователи и ключи VPN) | существует только на сервере |
| `/etc/wireguard` | другие узлы знают этот публичный ключ |
| `/root/cert`, `/root/.acme.sh` | сертификат панели x-ui и настройки его продления |
| `/root/hobot-metrics` целиком | секреты, которые git игнорирует, и незакоммиченные правки |
| `release.env` прокси | текущая версия — сразу при восстановлении |
| тома Alertmanager и Prometheus `hobot-metrics`, база Grafana | тишины, история метрик, пользователи и настройки |

Не копируются: прокси MaxApoc (compose, `.env`, сертификаты, `gateways.json` — git и vault), плагины Grafana (512 МБ, ставятся заново), fail2ban и агент Zabbix (ставятся установщиками).

- Базы SQLite — через `sqlite3 -readonly <база> ".backup …"`: согласованный снимок без остановки сервиса. `-readonly` — чтобы отсутствующая база была ошибкой: без флага `sqlite3` создаёт пустую базу, и копия тихо оказалась бы пустой (проверено на рабочем сервере).
- История Prometheus копируется на ходу: блоки — целиком, последние ~2 часа (журнал записи) могут оказаться неполными и при запуске обрежутся. Для истории метрик приемлемо.

**Последствия**
- (−) Список путей — переменная инвентаря: новое состояние на сервере (новый сервис) нужно добавить вручную. Учения и проверка содержимого копии ловят пропуск, целостность базы — нет.

<a id="adr-025"></a>
## ADR-025. Версионирование бакета, без блокировки объектов

**Решение.** В бакете включено версионирование; правило жизненного цикла: неактуальные версии удаляются через 30 дней, незавершённые загрузки — через 7. Удаление актуальных объектов по сроку не включается (уничтожило бы репозиторий).

**Альтернативы**
- *Блокировка объектов (WORM).* Отклонено: restic при каждом запуске удаляет свои файлы блокировок, `forget`/`prune` удаляют данные — под блокировкой копии падали бы каждую ночь.

**Последствия**
- (+) 30 дней можно вернуть объект, удалённый по ошибке или `prune`.
- (−) Владелец ключа может удалить и версии: от целенаправленного удаления защищает только домашняя копия.

**Как проверено:** копии с включённым версионированием проходят без ошибок.

<a id="adr-026"></a>
## ADR-026. fail2ban не входит в Ansible

**Контекст.** На рабочем сервере работает fail2ban, но не из этого кода: его поставил установщик панели 3x-ui (ограничение числа адресов на пользователя VPN) вместе со стандартной защитой sshd из пакета.

**Решение.** Не добавлять fail2ban в роль `security`. Вход только по ключу, пароль и root отключены, `LIMIT` на порт 22 — подбор пароля невозможен, а частота подключений уже ограничена. fail2ban остаётся зависимостью x-ui и ставится вместе с ним при восстановлении.

<a id="adr-027"></a>
## ADR-027. Восстановление: цели RTO/RPO и учения

**Цели**
- **RPO — до суток** (копия раз в сутки плюс до 30 минут задержки). Частота почти не влияет на объём (дедупликация), но увеличивает нагрузку и число снимков; для редко меняющихся данных суток достаточно.
- **RTO — меньше часа при переустановке того же VPS (адрес сохраняется):**
  - замерено ~7 минут автоматической части: чистая ВМ → Ansible 6 мин 26 с, восстановление копии 2,7 с;
  - ручные шаги (x-ui, WireGuard, `hobot-metrics`) — по процедуре, не замерены.
- **Новый адрес — дни, копии не помогают.** Адрес зашит:
  - в сертификат прокси — пересборка приложения и обновление у пользователей;
  - в сертификат панели x-ui;
  - в настройки клиентов VPN и узлов WireGuard.

  Поэтому при аварии — переустановка того же VPS, а не новый сервер.

**Учения**
- Ежемесячно (вместе с копией домой) — лёгкая проверка: база x-ui из домашней копии, целостность и число inbound-ов.
- Раз в квартал и при обновлении или откате версий x-ui, Grafana, Prometheus, при изменении списка копируемого — полные: чистая ВМ → Ansible → восстановление копии рабочего сервера в отдельный каталог → сверка.
- WireGuard, x-ui и Alertmanager `hobot-metrics` из копии рабочего сервера в тестовой среде **не запускаются**: тот же ключ туннеля, включённый бот x-ui и настройки оповещений мешали бы рабочему серверу.

**Как проверено (04.11.2026):** копия рабочего сервера восстановлена на чистую ВМ; 7 файлов совпали с живым сервером по хешам, в базе x-ui `count|max(id)` совпали; история Prometheus из копии — те же 18 блоков, читается той же версией; Grafana той же версии стартовала с восстановленной базой (`database: ok`, миграций не потребовалось).

**Не проверено:** переустановка у хостера и первый вход, раскладка файлов по местам, запуск x-ui, WireGuard и `hobot-metrics` из копии.
